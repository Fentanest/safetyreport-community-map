## 함께 수정한 항목과 새 회귀

- **PC 삭제 안내:** `web/templates/components/community_consent_card.html:207-227`은 `local_cleanup_pending`과 `writer_reset_pending`을 각각 누적 표시한다. 실제 응답은 `web/routers/community_route.py:284-299`에서 두 플래그를 같은 수준으로 반환하고 `act`가 `res.data`를 callback에 전달한다. `community-delete-message.spec.ts`의 네 조합이 Chromium/Firefox 로그에 포함됐다. 확인한 경로에서 회귀 없음.
- **모바일 analyze 정리:** async 뒤 `mounted` 확인, `RadioGroup`/dropdown 이관 및 null-aware map entry 등 전체 수정 diff를 읽었다. `flutter analyze` exit 0, 521개 테스트 통과, `duplicate_editor_radio_test.dart`가 대표 후보 선택 뒤 “수동 고정” 표시를 확인한다. 확인한 경로에서 회귀 없음. 실기기 화면 상호작용은 이번 재검증에서 직접 실행하지 않았다.
- **새 의미 회귀:** SOL-06의 `point_count`는 이제 신고일/완료일 위치의 합집합인데 `basis='report_date'`, 분모는 신고일 건수, KPI 문구도 신고일 기준이다. 완료일만 범위에 든 위 독립 재현에서 `value=1 > denominator=0`과 잘못된 빈 결과 안내가 함께 발생한다. 심각도 **중간**. 같은 사례를 API 스키마·KPI/빈 상태 렌더 테스트에 넣어야 한다.
- **쓰기 장벽의 범위:** 프로세스 안 SQLAlchemy 연결에는 적용되며 20초 배수 실패가 명시적 409로 변환된다. 크롤러 자식 프로세스의 시작 경쟁은 위 SOL-04로 남는다. 직접 `sqlite3.connect` 백업·체크포인트 경로는 데이터 writer가 아니지만 복원 중 일관된 백업을 보장하는 별도 직렬화도 없다. 다중 worker/외부 DB writer에 대한 프로세스 간 배타 테스트는 없다.

## 결론

**수정 후 재검토.** SOL-02와 SOL-04에 **높음 미해결** 경로가 남아 있으므로 감사 수정 병합 가능으로 판정할 수 없다. SOL-05의 실제 사용자 복구 경로와 SOL-06의 합집합 지표·빈 상태 설명도 보완해야 한다. 수정 뒤 해당 경계 사례의 회귀 테스트와 새 후보 SHA의 실행 로그를 다시 확인해야 한다.
