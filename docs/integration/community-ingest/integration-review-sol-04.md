## 새 회귀와 실행 증거 공백

1. **모바일 로컬 정리 실패 안내가 사라지는 경로(중간):** 중앙 삭제 성공 뒤 `confirmDeletion`이 로컬 DB 오류로 실패하면 `requestDeletion`은 `local_pending`을 돌린다(`M lib/community/upload_hooks.dart:61-68`). 그런데 카드가 `not_started`와 `unconfirmed`만 구분하고 `local_pending`은 일반 삭제 성공 문구로 보낸다(`lib/widgets/community_account_card.dart:564-583`). 이어 `handleContributionsDeleted`가 재시도해도 `CommunityWiring.onContributionsDeleted`는 `applyPendingDeletion`의 `false`를 `Future<void>`로 버리고(`lib/community/community_wiring.dart:51`; `capture/server_completed.dart:152-176`), `contributionsDeletedNow`는 예외가 없었다는 이유로 `true`를 돌린다(`lib/community/upload_hooks.dart:104-114`). 따라서 prepared가 남아도 실패 notice가 설정되지 않을 수 있다(`lib/community/gate/community_gate.dart:523-530`). 업로드는 표시 때문에 fail-closed로 유지되지만 사용자는 즉시 남은 정리와 재요청 필요를 알 수 없다. 게이트의 다음 성공 판정에서 unconfirmed notice를 설정하는 코드(`community_gate.dart:295-300`)는 있으나, 그 전의 응답을 대체하지 않는다. `local_pending`과 `applyPendingDeletion=false`를 실제 DB로 주입해 표시·문구·전송 0을 검증해야 한다.
2. **모바일 R4 실행 증거 누락(중간, 병합 차단):** 추적된 `evidence/2026-09-26-r4/mobile-live.log`는 **0바이트**, `mobile-unit.log`는 skip 문구와 sqflite warning뿐이며 passed/failed 요약이나 명령 종료 코드가 없다. `mobile-analyze.log`의 “40 issues found”는 오류 없는 정적 분석의 흔적일 뿐 새 삭제 테스트 실행 증거가 아니다. R3의 실행 로그는 이전 모바일 커밋 `96085981`의 결과다. 현 후보 `729bc3da`에서 `flutter test`와 실스택 테스트를 재실행하고 명령·후보 SHA·종료 코드·전체 테스트 수를 추적 로그로 남겨야 한다. 이 세션은 사용자 지정 파일 외 수정 금지와 이전 환경 제약 때문에 Flutter를 재실행하지 않았다.
3. **PC 성공 후 후처리 순서(낮음):** 중앙 삭제 성공 뒤 `save_writer(None)`가 `confirm_deletion`보다 먼저 실행된다(`PC web/routers/community_route.py:281-284`). writer 파일 삭제/fsync가 실패하면(`services/community_auth_store.py:291-297`) 중앙은 삭제했지만 표시가 prepared로 남고 라우트가 일반 예외로 끝난다. 업로드는 차단돼 데이터 노출은 없으나 재요청 안내가 곧바로 전달되지 않는다. 로컬 삭제 확정을 writer 파일 정리보다 먼저 수행하고, 이 실패를 주입해 사용자에게 정확한 상태를 반환하는 편이 안전하다.

## 결론과 다음 고정 후보의 최소 조건

**목표 브랜치 병합은 아직 승인하지 않는다.** 모바일 `local_pending`·`applyPendingDeletion=false`에서 즉시 정확한 안내와 업로드 차단을 확인하고, 모바일 capture 의도 파일 쓰기 실패 시 개인 저장 보류를 실제 DB로 검증해야 한다. `729bc3da` 또는 수정된 다음 후보의 모바일 단위·실스택 실행 결과를 유효한 추적 로그로 제출하면 다시 판정할 수 있다. PC writer 파일 후처리 실패 주입은 같은 재검토 때 확인할 낮은 심각도 항목이다.

이 판정은 운영 미검증 항목을 통과로 바꾸지 않는다. 병합 뒤 7일 감사에서 다룰 E08(fork/PR의 운영 호출 금지), I06(trigger만 다른 재전송), S-18(IP 헤더 위조), N-03(정책 불변 HTTP)은 매트릭스에서 여전히 `not-run/partial`이다(`map docs/integration/community-ingest/acceptance-matrix.md:38,47,67,72`). 운영 반영 전에는 읽기 전용 legacy/preflight, auth `202609260100` → map `202609260200` migration 순서·SHA, 호스팅 Kakao·JWT/CORS/키·Realtime/Storage 설정, Android/iOS 실기기 권한 순서·딥링크·백그라운드·복원, 릴리스 산출물 비밀/동의문 검사를 별도로 완료해야 한다. **공식 상세의 PC↔모바일 실경로 파서 동등성, 호스팅 Kakao, 실기기, 양 앱 `_run` 전체 경로와 PC broadcast 실부하 지연은 현재 미검증**이다.
