# 결정 사항과 미결정 사항

## 확정

### Supabase 중심 백엔드

Auth, Postgres, Edge Functions를 한 프로젝트에서 운영한다. R2는 당장 대체 저장소로 사용하지 않으며, 향후 공개 지도 JSON·타일 캐시가 필요할 때만 검토한다.

### GitHub Pages는 표시 전용

Pages는 정적 프런트엔드만 호스팅한다. 업로드와 DB 접근은 Supabase Edge Functions가 담당한다.

### 휴대폰 OTP

단순 번호 입력이 아니라 SMS OTP 확인을 완료한 번호만 기여자로 인정한다. 고유성의 정확한 표현은 `인증된 휴대폰번호당 하나`다.

### 정확한 위치

현재 신고 지도와 같은 마커·클러스터·과태료 비율 표시를 유지하기 위해 정확한 위경도와 주소를 사용한다.

### 개인별 스냅샷 교체

모든 업로드를 누적하지 않는다. 한 사용자의 마지막 정상 전체 스냅샷만 활성화한다.

### 피신고자 원문 미수집

차량번호, 신고번호, 본문, 첨부, 정확한 발생시각은 DTO와 DB 스키마에서 배제한다.

### 담당자 비공개 수집

담당자 이름은 `manager_counts` breakdown으로 수집해 비공개 영역에 저장하되 공개 API에는 포함하지 않는다. 두 레포의 현재 지도 집계 경로에는 담당자 필드가 없으므로 클라이언트 DTO 생성 시 담당자 집계를 추가한다. 공개 여부는 ADR-004에서 별도 검토한다.

### 연도 기준은 신고일

지도는 신고 활동을 보여주므로 연도는 신고일 기준으로 배정한다. 모바일 로컬 집계는 이미 신고일 기준이고, `safetyreport` 서버 통계는 답변일 기준이므로 업로드 DTO 변환 시 신고일 기준으로 다시 계산한다.

### 위치 키는 좌표 기반으로 시작

`round(lat,6)|round(lng,6)`의 SHA-256을 위치 키 시작값으로 쓰고 주소는 키에 넣지 않는다. 두 레포의 주소 정규화가 공백 정리 수준이라 표기 편차로 지점이 갈라지면 `contributor_count`가 과소집계되기 때문이다. 최종 확정은 ADR-003.

## 운영 데이터로 검증

- 사용자당 평균·최대 위치 지점 수
- 스냅샷 압축 전후 크기
- 동일 장소의 주소 표기 편차
- 위치별 서로 다른 기여자 분포
- 담당자 통계가 지도 사용성에 실제 필요한지
- D1/R2가 필요할 정도의 공개 API 트래픽인지
- Supabase Free DB와 egress 사용량

## 검토 중인 대안

### 별점주기 URL 접속으로 번호 확인 (SMS OTP 대체안)

사용자 DB의 답변완료 최근 건에 대해, 입력한 휴대폰번호가 들어간 안전신문고 별점주기 주소로 접속이 성공하면 확인된 번호로 인정하자는 안.

- 장점: SMS 비용이 없고, 번호가 실제 신고 이력과 결합되어 있음을 확인하므로 "이 신고 데이터의 주인"이라는 증명으로는 OTP보다 의미가 강하다.
- 한계:
  - 검증이 클라이언트에서 일어나므로 서버가 결과를 신뢰할 수 없다. 변조된 클라이언트가 "확인됨"을 주장하면 막을 방법이 없고, 이는 이 프로젝트의 "클라이언트 검증은 보안 경계가 아니다" 원칙과 정면 충돌한다.
  - 서버가 직접 검증하려면 신고번호가 포함된 URL을 중앙 서버로 보내야 해서 전송 금지 필드 원칙을 깨고, 외부 사이트의 비공개 URL 형식·접속 정책에 의존해 언제든 깨질 수 있다.
  - 번호의 현재 점유 증명이 아니다. URL이나 번호+신고번호 조합을 아는 제3자가 사칭할 수 있고, 번호가 재할당돼도 과거 신고 건으로 계속 "확인"된다.
  - Supabase Phone Auth를 쓸 수 없게 되어 동일 번호 → 동일 UUID 중복 방지, 세션·토큰 관리 전체를 자체 구현해야 한다.
- 현재 결론: 서버 측 고유성·인증은 SMS OTP를 유지한다. 별점주기 접속 확인은 업로드 전 클라이언트 로컬 사전 점검(번호 오타 방지, 신고 이력 결합 확인)으로만 선택 활용할 수 있다. OTP는 가입 시 1회이므로 비용은 사용자당 SMS 1~2건 수준이다.

### 신고번호 전역 중복 제거 (전화번호·auth.users 대체안)

전화번호 인증과 `auth.users`를 없애고, 신고번호를 수집해 업로드 간 중복 신고를 전역으로 제거하자는 안.

- 장점: SMS 비용과 전화번호 PII가 사라지고 온보딩이 단순해진다. 같은 사람이 번호를 바꾸거나 계정을 여러 개 써도 정확히 중복 제거된다.
- 한계:
  - 신고번호는 신고자 한 명에게만 귀속되므로, 정직한 데이터에서 스냅샷 교체 방식보다 더 걸러내는 것은 "한 사람의 복수 계정" 경계 사례뿐이다. 얻는 정합성 이득이 작다.
  - 중복 판정을 하려면 개별 신고 단위 데이터와 신고번호(또는 해시)를 수집해야 해서, "개별 레코드를 받지 않는다"와 "신고번호를 받지 않는다"는 두 핵심 원칙을 동시에 뒤집는다. 신고 한 건 = 정확 좌표 + 상태 + 기관 + 담당자 조합이라 재식별 위험이 집계 방식보다 크다. HMAC pepper 해시로 외부 역산은 막을 수 있지만 서버는 여전히 특정 신고번호의 참여 여부를 조회할 수 있고, 신고번호 체계가 규칙적이면 pepper 없는 해시는 전수 대입에 뚫린다.
  - 위조 데이터에 무력하다. 가짜 신고번호는 전부 고유해서 중복 제거가 아무것도 걸러내지 못하고, 인증이 없으니 IP 제한 외에 남용을 묶을 단위도, 격리·롤백 단위(사용자 스냅샷)도 없다.
  - 중복 제거 자체가 공격면이 된다. 실제 신고번호를 추측·입수한 공격자가 쓰레기 데이터를 먼저 올리면 본인의 진짜 업로드가 중복으로 버려지고, 신원이 없어 충돌 시 누구 것이 진짜인지 판정할 수 없다. 상태 갱신(처리중→수용) 재업로드도 아무나 덮어쓸 수 있다.
  - `contributor_count`와 신뢰도 표시가 사라지고, "내 기여 철회·삭제" 요청을 인가할 방법이 없어진다.
- 현재 결론: 단독 대체로는 채택하지 않는다. 전화번호 제거가 목적이면 익명 자격증명(Supabase anonymous auth)+기여 코드 연결 방식을, 중복 제거 강화가 목적이면 0단계에서 복수 계정 중복이 실제 발생하는지 측정한 뒤 비공개 전용 HMAC 신고번호 해시를 중복 방지 키로만 좁게 추가하는 방안을 각각 검토한다.

## 장래 ADR 후보

- `ADR-001`: SMS 사업자 선택
- `ADR-002`: 공개 최소 기여자 임계값
- `ADR-003`: 위치 키 알고리즘 (좌표 단독 vs 주소 포함, 0단계 표기 편차 측정 후)
- `ADR-004`: 담당자 정보 공개 여부
- `ADR-005`: Edge 집계와 예약 집계 중 선택
- `ADR-006`: R2/PMTiles 공개 캐시 도입 여부
- `ADR-007`: 공개 지도 SDK와 타일 공급자
