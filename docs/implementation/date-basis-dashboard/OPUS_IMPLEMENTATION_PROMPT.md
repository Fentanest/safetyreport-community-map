## U01. 신고일/답변일 선택을 모든 조회의 공통 기준으로 만들기

### 1.1 가장 중요한 데이터 선택 규칙

권한과 공개 정책을 통과한 신고의 최신 대표를 확정한 뒤, 다음 **한 날짜만** 기간 조건에 사용한다.

```ts
// 개념 모델이다. 현재 저장소 타입·RPC·권한 흐름에 맞춰 구현한다.
type DateBasis = 'report_date' | 'completed_date';
const selectedDateOf = (
  report: { report_date: string | null; completed_date: string | null },
  basis: DateBasis,
): string | null => basis === 'report_date' ? report.report_date : report.completed_date;

const cohort = canonicalEligibleReports.filter(report =>
  isValidDate(selectedDateOf(report, scope.date_basis)) &&
  insideInclusiveKstDateRange(selectedDateOf(report, scope.date_basis), scope.start, scope.end) &&
  matchesAppliedDimensions(report, scope)
);
```

- 신고일 기준이면 **신고일만** 범위 안인지 검사한다. 답변일이 범위 전/후라는 이유로 빼지 않는다.
- 답변일 기준이면 **답변일만** 범위 안인지 검사한다. 신고일이 범위 전/후라는 이유로 빼지 않는다.
- 두 날짜의 AND 조건도, 두 날짜의 OR 조건도 최종 모집단 규칙으로 쓰지 않는다.
- `reported`와 `done`을 각기 다른 날짜로 골라 카드별로 섞는 기존 구조를 제거/개편한다.
- 지도·주소·지역·기관·담당자·차량·기여자·월별 차트·내 신고 비교는 **동일하게 선택된 신고 identity 집합**에서 파생한다.
- 같은 신고의 속성인 다른 날짜는 버리지 않는다. 처리기간, 신고일 수, 맞춤 통계의 별도 날짜 축 등에 그대로 쓸 수 있다.
- 이 기능은 ‘해당 날짜에 속한 신고의 현재 공개 가능한 최신 결과’다. 과거 시점의 상태를 복원하는 as-of 기능으로 설명하지 않는다.
- 공유 대상은 현재 공개 적격 자료 그대로다. 신고일 선택을 추가했다고 미완료 신고 전체까지 수집/공개하는 기능으로 바꾸지 않는다.

필수 예시: 기간 `2025-07-01~2025-08-31`.

| 신고일 | 답변일 | 신고일 기준 | 답변일 기준 |
|---|---|---|---|
| 2025-07-10 | 2025-09-03 | 포함. 9월의 현재 답변·처분도 사용 | 제외 |
| 2025-05-20 | 2025-08-05 | 제외 | 포함. 5월 신고 속성도 보존 |
| 2025-08-15 | 2025-08-20 | 포함 | 포함 |
| null | 2025-08-20 | 제외(선택한 날짜 미상) | 포함. 소요일수·신고일 수에서만 결측 처리 |
| 2025-08-25 | null | **기존 공개 정책상 답변 완료로 확인된 자료이면 포함** | 제외(선택한 날짜 미상) |

마지막 행에서 답변일이 없다는 이유로 `answered()` 등의 부수 조건이 신고일 기준 모집단을 다시 제거하지 않게 한다. **완료 상태와 완료일 존재는 분리**한다. 공개 부적격·미완료 자료를 새로 허용하라는 뜻이 아니다. 공인된 완료 여부는 기존 원천·계약 규칙을 따른다.

### 1.2 건수·분모·결측 정의

- N: 선택된 공개 적격 고유 신고 수.
- C: 그 안에서 답변 완료로 확인된 신고 수. 현재 서비스의 정상 공유 자료에서는 N=C일 수 있다. 같은지 실제 원천 규칙으로 확인하고, 서로 다른 날짜를 사용해서 차이를 만들지 않는다.
- A/P/R: 그 집합에서 수용/일부수용/불수용으로 확인된 신고 수.
- K=A+P+R: 결과가 확인된 신고 수.
- F/W: 해당 집합 중 과태료/경고·계도 처분으로 확인된 신고 수.
- 수용률=A/K, 일부수용률=P/K, 불수용률=R/K, 과태료처분율=F/C, 계도처분율=W/C.
- 결과 미상·금액 미상·미공개·날짜 미상은 각각 구분한다. 분모 0은 null/—, 실제 분자 0·양의 분모는 0%다.
- `fine`은 금액 유무가 아니라 처분 분류로 센다. `warning`에 범칙금을 합치지 않는다.
- 처리기간은 실제 답변일−실제 신고일의 KST 달력일 차이다. 기간 시작/끝으로 날짜를 잘라 소요일수를 줄이지 않는다. 한 날짜가 없거나 역전이면 그 지표에서 사유별 제외만 한다.
- 신고일 기준으로 선택된, 답변일 미상의 공식 완료 신고도 상태·처분이 확인돼 있다면 그 값의 집계에는 사용할 수 있다. ‘답변 날짜 미상’은 ‘답변 없음’이 아니다.
- 참여자 수는 선택된 신고 identity에 연결된 허용된 기여 계정을 distinct로 센다. 대표행 소유자만 세어 공동 기여자를 없애거나 다른 기간의 신고 기여자를 끼워 넣지 않는다.
- 전체/내 신고는 같은 날짜 정책과 데이터 버전, 각각의 기존 소유권·대표 규칙을 적용한다. 내 신고를 전체의 대표행 소유자 필터만으로 대체하지 않는다.

### 1.3 두 날짜 UI의 동작

상단은 `[답변일 ▾] [2025.07.01 — 2025.08.31 ▾]` 형태로 날짜 옆에 둔다. 상세 필터도 날짜 영역 바로 옆에 동일한 `신고일 / 답변일` 선택기를 둔다. 실제 의미는 `completed_date`=답변일이며, 과태료 실제 부과일로 오해시키지 않는다.

- 최초 기본값은 **답변일**. 명시적 URL/공유/화면 인계 > 같은 사용자의 저장 설정 > 기본값 순으로 복원한다.
- 기준을 바꿔도 직접 입력해 둔 시작/종료일은 바꾸지 않는다. 적용 조건이 바뀌어 결과가 0건이면 그대로 0건으로 처리한다.
- 상단 기준 변경은 현재 정상 적용 기간과 함께 원자적으로 반영해 조회 1회. 상세 필터는 draft에만 반영하고 `적용` 시 기준·날짜·다른 필터를 함께 1회 반영한다.
- 상세 필터 취소는 적용된 상단 조건을 변경하지 않는다. 다시 열면 최신 적용 조건으로 초기화한다.
- 미완성·잘못된 날짜 입력을 자동으로 다른 날짜로 교정하거나, 기준 변경 이벤트를 이용해 우회 적용하지 않는다. 입력값·포커스를 유지하고 오류를 표시한다.
- 두 UI는 하나의 상태 모델을 편집한다. 독립 state 두 개를 effect로 서로 덮어쓰는 구조를 피한다.
- 적용 칩/상단 제목/로딩의 이전 조건 설명에 날짜 기준까지 표시한다. 선택 범위가 같아도 신고일↔답변일은 다른 조건이다.
- 상단 기준 토글 때문에 상세 날짜 입력이 재마운트되어 숫자 한 글자마다 포커스가 이동하는 회귀를 막는다.
- `전체` 분류 버튼과 `전체 기간`을 구분한다. 전체 분류는 날짜·기준을 초기화하지 않는다.

### 1.4 데이터 조회·대표 선정·비교기간

대상 파일을 실제 따라가며 구현한다: `server/aggregate.ts`, `places.ts`, `compare.ts`, `statistics.ts`, `publicHandler.ts`, `personalHandler.ts`, 두 Edge 엔트리와 `internal_analytics_v2_facts`, `internal_my_analytics_source` 등 실제 활성 RPC.

**최신 대표를 확정하고 날짜를 적용한다.** 기간을 먼저 제한해 최신 답변이 후보에서 빠지고 오래된 답변이 다시 대표가 되지 않게 한다. 후보 identity를 인덱스로 찾은 뒤 그 identity들의 허용된 관련 이력을 조회하는 최적화는 가능하지만, 최종 대표 판단에 필요한 최신 행을 누락하면 안 된다. 개인정보 공개 허용·동의 계보·신고번호 결합·동일 신고 중복 제거·내 신고 소유권을 유지한다.

- 같은 identity의 과거 답변 8월/최신 답변 9월, 신고일 5월이라면: 답변일 8월 조회에서 과거 행을 대표로 부활시키지 않는다. 신고일 5월 조회는 그 identity의 최신 9월 결과를 보여준다.
- 기존 SQL의 `report_date OR completed_date`로 넓게 읽는 것은 전환 중 후보 조회에만 제한적으로 허용할 수 있다. 최종 응답은 반드시 선택 기준의 정본 집합이어야 한다. 과도한 두 날짜 OR 스캔은 최적화한다.
- 증감의 직전 기간도 현재와 **같은 date_basis**, 같은 길이, 같은 다른 필터/포커스로 계산한다. 비교용 행을 현재 건수·결측·주소 수에 섞지 않는다.
- 비교를 제공하지 않는 상세·맞춤 통계 요청까지 무조건 직전 기간을 읽지 않는다. 필요한 경우만 조회한다.
- 날짜만 전국으로 읽은 100,000행 제한 때문에 작은 지역/기관 검색도 실패하는 경로를 점검한다. 권한·대표 선정 정합성을 보존하는 DB 집계/단계적 조회로 개선하되 한도를 무조건 해제하지 않는다.
- 현재 값 조회에 성공하고 비교 데이터만 제공 범위 밖이면 현재 결과는 유지하고 비교만 미제공으로 표시한다. 부분 비교를 완전한 직전기간 통계라고 표시하지 않는다.
- SQL 변경은 새 증분 migration으로 한다. 함수 인자 변경으로 생기는 동명 overload·권한 grant/revoke·RPC 선택 혼동까지 검사한다.

### 1.5 공통 계약과 상태 키

`Scope.date_basis`를 전역 정본으로 삼는 것을 우선한다. 실제 타입명은 저장소에 맞춰도 되나, 하나의 요청 안에서 독립적인 두 기준이 경쟁해서는 안 된다.

- 맞춤 통계의 기존 `spec.date_basis`와 새 전역 기준은 하나로 정규화한다. 전환 호환 필드로 둘 다 받는다면 값이 다를 때 400 등 명시적 오류로 거부한다. 어느 한쪽을 조용히 우선하지 않는다.
- 공개/개인 통계, 기관/법규 목록, 주소 상세, 정밀 핀, 지역 집계, 후보 검색, 맞춤 통계에 모두 같은 기준을 전달한다.
- 응답은 사용한 기준·기간·정책 버전·데이터 버전·포커스가 요청과 일치함을 검증할 수 있어야 한다. `cohort_policy_version` 같은 명시적 버전을 두고 실제 값은 문서화한다.
- `CountMetric.basis`, `DurationSummary.basis`, `FineAmountSummary.basis`, analytics의 basis, 월별 메타 등 기존 `completed_date` 리터럴을 감사한다. ‘모집단을 고른 날짜’와 ‘계산에 쓰는 속성’은 별도 의미로 정의한다.
- 캐시/중복 요청 키는 인증된 계정 경계·date_basis·start/end·전체 필터·포커스·선택 대상·정렬/페이지(해당 자원)·데이터/정책 버전을 포함한다.
- URL, 뒤로/앞으로, 새로고침, 저장 설정, 공개 링크, 화면 인계, 엑셀 조건에도 date_basis를 보존한다.
- 날짜 기준이 없는 옛 일반 지도 링크는 새 기본 답변일로 해석하되 첫 복원 시 기준을 명확히 표시하고 새 URL로 정규화한다. 옛 신고일/답변일을 명시한 맞춤 통계 구성은 **그 명시적 기준을 보존**한다. 이번에도 신고일 기능을 없애거나 답변일로 강제 이관하지 않는다.
- 의미/버전 충돌이 있으면 안내·명시적 변환·지원 불가 중 하나로 처리한다. 이름만 바꾸고 옛 응답을 새 의미로 쓰지 않는다.

### 1.6 지도·목록·표식

- 선택된 집합에서 주소를 한 번 묶는다. 다른 날짜가 기간 밖인 주소도 정상 핀/목록 대상이다.
- `hiddenNote`의 ‘신고가 없고 답변만 있는 곳은 비율 지표에서 보임’ 안내와 이에 연결된 날짜별 숨김 분기를 제거한다. `DataGuide`·도움말·툴팁도 수정한다.
- **신고 수 모드=주소별 핀·클러스터**, **수용률/불수용률/과태료 모드=행정구역 색칠·원형 핀 0**은 유지한다. 날짜 때문에 장소를 빼는 것과 지표에 따른 렌더러 전환을 혼동하지 않는다.
- 비율 분모 0인 행정구역은 계산 불가 상태로 남기고, 날짜 밖이라는 설명으로 없애지 않는다.
- 주소·좌표가 없어 지도에 못 찍는 신고는 통계에서 제거하지 않는다. `통계 N건 / 지도 배치 가능 M건` 등 필요시 범위를 설명한다.
- 압축 노드 수를 주소 ‘곳’ 수로 부르지 않는다. 서버에서 반환한 정확한 주소 distinct 수를 쓴다. 확대만으로 같은 범위의 주소 수가 바뀌어 보이지 않게 한다.
- 지역 귀속은 각 원 신고 위치의 현재 행정구역이다. 주소의 표시용 대표 좌표·처리기관 소재지를 대신 사용하지 않는다.
- 내 장소 표식·내 신고 숫자·함께 신고 여부·지역의 내 신고 정렬은 같은 선택 집합을 사용한다. ‘내 신고 0건’인데 해당 집합의 내 장소라고 표시하는 모순을 제거한다.

### 1.7 이전 정밀조회 응답 유입 차단 — D10 필수 수정

`Dashboard.tsx::onView`의 타이머, `loadPlacesInView`, `refined`, `mapPoints` 병합을 함께 수정한다.

- 정밀조회 상태에 요청 당시 전체 scope(date_basis 포함), viewer 경계, dataset/policy version, view_bbox, request generation을 남긴다.
- scope/기준/계정/모드가 바뀌면 이전 예약 타이머·클라이언트 요청을 취소/무효화한다.
- 응답 commit과 mapPoints merge 양쪽에서 **현재 표시 snapshot의 조건**과 일치하는지 확인한다. 버전만 같다고 채택하지 않는다.
- 상위 snapshot이 바뀌기 전 마지막 정상 화면을 유지할 수는 있지만, 그 화면의 조건을 명확히 표시한다. 새 snapshot과 옛 정밀 핀의 혼합은 금지한다.
- 같은 날짜 범위·같은 데이터 버전에서 ‘신고일 A→답변일 B’ 전환도 서로 다른 요청이다.
- 오래된 catch/finally가 최신 로딩을 끄거나, 해제한 주소를 되살리거나, 최신 빈 결과를 덮지 않게 한다.
- 지도 인스턴스를 재생성하거나 강제 새로고침해서 해결하지 않는다.

### 1.8 월별 추이·날짜 축·차량 분석

**메인 월별 그래프는 선택한 날짜 기준으로 그룹까지 통일한다.** 신고일 기준=신고월, 답변일 기준=답변월. 선택된 집합에 속한 7월 신고·9월 답변은 신고일 기준 그래프에서 7월 처리결과에 포함한다. 9월 점을 추가하거나 9월 답변이라는 이유로 결과에서 제외하지 않는다.

- 월별 ‘건수’와 복수 처리결과 비율은 같은 월의 같은 집합을 쓴다. 수용/불수용/일부수용/과태료 1~4개, 전체/내 신고 최대 8선은 유지한다.
- `건수 / 처리결과 비율` 전환은 유지한다. 정상 자료에서 신고 건수와 답변 확인 건수가 완전히 같은 선이라면 중복 의미를 명확히 하거나 하나로 합쳐 표시하고, 답변 확인 수치는 표/툴팁에 보존한다. 다른 날짜축을 쓰는 옛 두 선을 남기지 않는다.
- 제목은 `신고월별 처리결과` 또는 `답변월별 처리결과`처럼 표시한다. ‘수용률 계산 분모’와 날짜 기준을 혼동하지 않는다.
- 맞춤 통계로 보내는 행 차원은 선택 기준에 맞는 `report_month`/`completed_month`, 날짜 기준·선택 지표·집단·조건을 그대로 넘긴다.
- 맞춤 통계에서 사용자가 명시적으로 다른 날짜 차원을 고르는 것은 허용한다. 예: 답변일 8월 집합을 신고월별로 나눠 5월 열이 나오는 것은 정상이다. 이것을 ‘8월 답변 신고의 신고월별 분류’라고 표시하고 최종 집합을 몰래 재필터링하지 않는다.
- 차량 TOP5·차량 distinct·반복 신고일 분포는 같은 집합을 사용한다. 반복 신고일은 그 집합의 원래 신고 날짜를 distinct로 세며, 날짜 기준이 답변일이라고 답변일 수로 바꾸지 않는다. 재범률로 표현하지 않는다.

**연속 날짜 축:** 데이터가 있는 달만 나열하지 않는다. 메인과 맞춤 통계에서 선택 기준의 시간축은 선택 범위의 calendar spine에 값을 key로 결합한다. 1월·3월 자료만 있어도 2월을 남긴다. 집계가 완료된 기간의 실제 0건은 건수 0, 비율 분모 0은 null/끊긴 선, 미제공 구간은 no_data로 구분한다.

다른 날짜를 분류축으로 쓴 경우 선택 날짜 범위를 그 다른 날짜축에 강제하지 않는다. 실제 해당 속성의 범위/명시적 필터를 사용해 날짜 간격을 보존한다. 명시적으로 1월·3월만 선택했으면 2월이 조회됐다고 꾸미지 않고 불연속 선택을 표시한다. 보충된 축도 결과 크기 한도에 포함한다.

### 1.9 달력·전체 기간·결측 진단

- `todayKst`, 선택 범위, 선택 기준별 `data_min/max`, 실제 소스 갱신 시각, 월별 covered interval을 분리한다.
- ‘이번 달 진행 중’은 실제 KST 이번 달인지로 판정한다. 마지막 데이터가 6월이라는 이유로 6월을 9월 현재의 진행 중인 달로 부르지 않는다.
- 8월10~20일을 조회하면 ‘일부 기간(8.10~8.20)’을 표시한다. 월 전체처럼 보이게 하지 않는다.
- `최근 N일`은 KST 오늘을 기준으로 하도록 정리한다. 데이터가 오래됐으면 ‘최근 자료: …’를 별도로 알린다. 소스 최신일 기준 프리셋을 남긴다면 그 이름에 기준을 명시하고 오늘 기준처럼 표시하지 않는다.
- `전체 기간`은 선택한 날짜의 공개 가능 전체 이력 min/max에서 가져온다. 신고일과 답변일을 합친 bounds로 같은 값을 쓰거나 현재 필터의 마지막 일부 응답으로 추정하지 않는다. 기준 변경만으로 날짜를 바꾸지 않고 사용자가 ‘전체 기간’을 다시 눌렀을 때 재설정한다.
- 선택 기준상 완전히 자료가 없는 유효한 기간은 가능하면 정상 0건/해당 기준 자료 없음으로 응답한다. ‘잘못된 달력 날짜’와 ‘적격 자료가 없음’을 구분한다.
- 선택 날짜가 없는 신고는 그 기간의 소속을 정할 수 없다. 직전 기간까지 읽어온 raw facts의 결측 수를 현재 기간 누락처럼 합산하지 않는다.
- 진단값은 `scope 밖 전체 진단`인지 `선택 집합에서 다른 날짜가 없는 건`인지 구분한다. 필요한 진단을 계산하지 못하면 미제공으로 두고 거짓 0건을 만들지 않는다.
- 전체/내 신고의 누락 수는 각각 반환한다. 둘을 더해 고유 제외 건수라고 표시하지 않는다. 다른 필터를 반영한 집합에서 계산한다.
- 미래·역전·잘못된 날짜를 업로드일/오늘/다른 날짜로 대체하지 않는다. 선택 날짜가 유효하면 다른 날짜 이상은 해당 지표의 품질 문제로 분리한다. 별도 기존 격리 정책이 있다면 이유를 문서화하고 원본을 보존한다.

## U02. 주요 통계를 지도 위 한 줄로 이동하고 선택 포커스에 연결

### 2.1 레이아웃

필터바 아래, 지도와 오른쪽 상세를 포함한 영역 **바로 위 전체 폭**에 `주요 통계`를 하나만 둔다. 오른쪽에 같은 전역 KPI를 중복 렌더링하지 않는다. 지도 핀을 누르거나 해제해도 이 박스의 자리는 없어지지 않는다.

- 이 작업의 ‘항상’은 컴포넌트/자리 유지다. 새로운 대형 sticky/fixed KPI를 추가해 지도와 표를 가리지 않는다.
- 데스크톱은 지표 셀을 가로 한 줄로 배치한다. 각 셀 안에서 라벨/큰 숫자/보조값 2~3줄은 허용한다. KPI 카드 자체를 2×4 그리드로 되돌리지 않는다.
- 포커스 라벨(전국/지역/주소), 날짜 기준·기간, 갱신 상태를 명확히 둔다. 긴 주소는 줄임표와 전체 확인 수단을 제공한다.
- 기존 지표를 잃지 않는다: 신고 건수, 답변 확인 건수, 수용/일부/불수용률, 과태료 건수·율, 계도 건수·율, 처리기간, 확인 금액, 평균 별점·평가 수, 장소 수, 참여자 수.
- N=C이면 신고 셀 보조값에 ‘답변 확인 C건’을 함께 두어 같은 숫자를 독립 대형 셀로 중복하지 않을 수 있다. 기존 확인 건수를 완전히 삭제하거나 둘이 다를 때 같은 값으로 바꾸지는 않는다.
- 금액·장소·참여자처럼 주요 수치도 가로 흐름에 배치한다. 정의·증감 상세는 기존 펼치기에서 보존하되 주요 값들을 전부 접힌 영역에 숨기지 않는다.
- 초기 높이는 대략 90~120px 범위에서 검수한다. 값은 18~24px, 라벨/보조값은 읽을 수 있는 크기를 유지한다. 고정 높이로 내용을 잘라내지 않는다.
- 폭이 부족하면 **KPI 내부만 가로 스크롤**한다. 모바일에서도 KPI 셀은 한 줄 흐름이다. 페이지 전체 가로 넘침, 작은 글자로 모두 우겨 넣기, 의미 없는 두 번째 KPI 행은 금지한다.
- 가로 스크롤 가능함을 알 수 있는 가장자리 표시/스크롤 조작과 키보드 접근성을 제공한다. 선택된 값과 포커스가 카드 밖으로 사라지지 않게 한다.
- 다크/라이트 토큰을 사용한다. 기존 ‘1건’만 다른 뱃지는 부활시키지 않는다.

### 2.2 포커스의 정본과 영향 범위

| 상태 | 주요 통계·오른쪽 상세가 읽을 집합 |
|---|---|
| 개별 주소 핀 선택 | 적용된 cohort ∩ 선택 주소 |
| 주소 해제 + 시도/시군구 선택 | 해당 적용 지역의 cohort |
| 주소 없음 + 자동 범위 ON | 현재 **반영 완료된** bbox와 다른 필터의 cohort |
| 주소 없음 + 자동 범위 OFF | 현재 명시적으로 적용된 지역/필터/bbox의 cohort |
| 지역·bbox 선택 없음 | 현재 날짜/법규 등 조건에 맞는 전국 cohort |

- 날짜 기준/범위/전역 조건 `Scope`와 상세 포커스 `Focus`를 분리한다. 주소 선택이 전역 기간·법규·기관 조건을 초기화하지 않는다.
- hover는 프리뷰에만 쓴다. 마우스를 지나가는 것만으로 KPI가 바뀌지 않는다.
- 주소 핀 선택/해제의 영향은 **상단 KPI + 오른쪽 상세 + 해당 범위 담당자 차트**다. 아래 전역 법규표·기관표·월별/처리기간 차트를 주소 하나로 몰래 제한하지 않는다. 하단에 적용 범위/날짜를 짧게 표시해 두 대상이 구분되게 한다.
- 하단까지 좁힐 때는 사용자의 명시적인 전역 필터 적용을 사용한다. 새 별도 기능을 임의 추가할 필요는 없다.
- 기존 같은 핀 재클릭·선택 해제 버튼·Esc·빈 지도 클릭, 선택 링·z-index·선택 표시를 유지한다. 해제하면 직전 적용 범위 KPI로 돌아간다.
- 자동 갱신 OFF에서 단순 지도 이동은 통계 포커스를 바꾸지 않는다. 이전 적용 bbox가 남아 있다면 칩과 대상 제목에 표시하고, OFF만으로 이를 전국으로 바꾸지 않는다.
- 지도 색칠 모드에서는 지역 선택이 같은 지역 포커스/필터 흐름으로 연결된다. 기존 핀 선택 상세는 제거/해제하고 지역 정보로 복귀한다.
- 압축 클러스터 클릭은 기본적으로 확대·주소 탐색이다. 무게중심이나 클러스터 bbox를 단일 주소로 취급하지 않는다. 그룹 통계를 실제로 지원하는 기존 기능이면 정확한 member 집합을 쓰고 ‘주소 N곳 묶음’이라고 표시한다. 단순 합으로 중앙값·distinct를 만들지 않는다.

### 2.3 전체 값이 있는 포커스 API/모델

기존 `KpiPanel`/`ScopeDetailsPanel`/`PlaceDetailsPanel`을 동일한 `SummaryModel` 등으로 어댑트하는 구조를 권한다. 새 타입명은 제안이며 구현됐다고 가정하지 않는다.

- 포커스 응답은 scope/date_basis, focus key, dataset/policy version, 주요 summary, 제공 가능 여부·결측, 필요시 전체/내 비교를 함께 검증할 수 있어야 한다.
- 주소 요약에 현재 금액·기간·별점·참여자·장소/답변 수가 없다면 **서버 집계와 DTO/Zod/client까지 추가**한다. 전역 overview 값을 주소 카드에 붙여 빈 칸을 메우지 않는다.
- 기관·담당자 목록은 페이지가 나뉘어도 summary는 전체 포커스 집합에서 계산한다. 상위 5/100개 합으로 대체하지 않는다.
- 주소 장소 수=그 주소에 속하는 집합의 distinct 주소, 참여자 수=같은 identity 집합의 공개 적격 기여자 distinct다. ‘주소니까 참여자 1명’ 식의 추정은 금지한다.
- 평균/중앙값/금액 합계/평균 별점은 해당 원 신고에서 공통 함수를 사용해 계산한다. 평균의 평균 금지.
- 핀 focus의 이전기간 증감을 지원하려면 같은 주소·같은 다른 조건·같은 기준의 직전기간을 조회한다. 지원하지 않으면 비교 미제공이지 전국 증감을 가져오면 안 된다.
- 내 신고 비교 ON이면 주소/지역별 내 요약도 정확히 일치시킨다. 내 포커스 응답 전에는 내 영역만 로딩/미제공 상태로 두고 전국의 내 수치를 대입하지 않는다.
- 인증은 기존 JWT 검증 경로를 재사용한다. 서버의 user id 확정은 클라이언트 focus/필터로 바꾸지 않는다.

### 2.4 요청 중 표시와 데이터 일관성

- KPI 컨테이너는 남긴다. 선택 즉시 ‘주소 정보를 불러오는 중’을 표시하되, 아직 남아 있는 숫자가 이전 대상이면 그 사실을 밝힌다. 새 대상 제목에 이전 숫자를 달아 확정값처럼 보이지 않는다.
- 제목·숫자·분모·차트·기준은 동일한 focus snapshot으로 원자적으로 교체한다.
- P1 지연→P2 선택, P1 지연→해제, 전역 basis 변경→P1 응답 도착, 계정 변경→응답 도착을 모두 차단한다.
- 같은 snapshot을 여러 카드가 구독한다고 summary API를 중복 호출하지 않는다. 기존 QueryActivityRegistry/RefreshController를 우회하는 별도 재시도 루프를 만들지 않는다.
- 새로운 focus에서 일부 필드만 미지원이면 해당 셀에 표시한다. 위에서 이미 읽은 전역 값으로 채우거나 미지원=0으로 만들지 않는다.

## U03. 건수·비율 복합 열의 정렬을 사용자가 선택

### 3.1 공통 열 메뉴

한 셀에 건수와 비율이 동시에 있으면 헤더 클릭/키보드에서 다음 메뉴를 제공한다.

```text
과태료 정렬
  건수 많은 순   ↓
  건수 적은 순   ↑
  비율 높은 순   ↓
  비율 낮은 순   ↑
```

현재 정렬은 헤더와 표 도구줄에 `과태료 · 비율 ▼`처럼 남긴다. 활성 헤더 색/배경, `aria-sort`, 메뉴 선택 상태를 일치시킨다. 오름/내림 아이콘만 있고 어떤 값 기준인지 알 수 없는 상태를 만들지 않는다.

- 하나의 숫자만 있는 열은 클릭으로 내림/오름 전환해도 된다.
- 건수/% 열이 아니면 의미에 맞춘다. 예: 평균 별점+평가 수는 ‘평균 점수/평가 건수’, 내 수용률+차이는 ‘비율/%p 차이’다. 차이를 %로 바꿔 쓰지 않는다.
- 수용·일부·불수용은 K 기준 비율, 과태료·계도는 C 기준 비율로 정렬한다. UI가 표시한 비율과 같은 산식이어야 한다.
- 메뉴를 열기만 해서는 조회하지 않는다. 선택 시 sort key·방향·page=1을 한 번에 갱신한다.
- 한글 IME 검색·열 선택·기관/담당자 전환·경찰/비경찰·내 비교·새 date_basis와 함께 동작한다.

### 3.2 적용 대상과 데이터 배선

최소 `EntityTable.tsx`(기관/담당자 모두), `LawTable.tsx` 및 각각의 전체 보기/확장 모달/표 보기에서 해당 복합 열을 지원한다. 이들 외의 사용자용 데이터 표도 공통 열 정의를 조사해 같은 형태에 재사용한다. 단순 KPI·데이터 없는 설명표에는 정렬 UI를 억지로 추가하지 않는다.

현재 `ENTITY_COLUMNS`의 단일 `sort`를 `sortOptions` 등으로 확장하고, renderer·header·열 선택·API enum·정렬 comparator가 하나의 registry를 사용하게 한다. `sort_by`/`sort_value` 또는 개별 metric key 등 wire 형식은 기존 계약에 맞춰 결정하되 자유 SQL/열 이름을 받지 않는다.

- **필터 → 전체 대상 집계 → 정렬 → 페이지 처리** 순서다. 첫 20행/상위 100행/상위 300법규만 로컬 정렬하고 ‘전체 순위’인 것처럼 표시하지 않는다.
- 현재 법규표 전체 API가 부족하면 실제 정렬 가능한 목록 경로를 추가/확장한다. DOM에 있는 행만 정렬하고 완료 처리하지 않는다.
- 같은 값은 안정된 이름·고유키로 정렬해 페이지 간 중복/누락을 막는다.
- 비율은 반올림 전 수치 또는 안전한 분자/분모 비교로 정렬한다. ‘33.3%’ 문자열끼리 사전식 비교하지 않는다.
- null/분모0/미지원은 오름·내림 **모두 마지막**으로 둔다. 실제 0건/0%는 정상 값이다.
- `fine_count=null`인데 `?? 0`으로 비율 0%를 만든 기존 표시 경로도 정렬 구현과 함께 교정한다.
- 서버 검색/필터/기준/정렬에 맞는 total을 반환한다. 페이지가 사라지면 page=1 등 명확한 규칙으로 복구한다.
- 개인 지표 정렬을 제공하면 인증된 개인 경로에서 전체 대상의 개인 집계를 계산한다. 상위 50개 개인 비교 요약에 없는 기관을 ‘내 0건’으로 간주해 정렬하지 않는다. 없다는 것이 확정된 값과 아직 조회되지 않은 값을 구분한다.
- 표에서 선택한 정렬을 차트/엑셀로 인계할 때 행 기준을 보존한다. 엑셀은 현재 페이지뿐 아니라 적용된 전체 결과를 올바른 정렬로 내보낸다.

### 3.3 인수 예시

기관 A: 답변100·과태료20(20%). 기관 B: 답변5·과태료5(100%).

- 과태료 건수 많은 순: A → B.
- 과태료 비율 높은 순: B → A.
- 역방향도 각각 반대로 작동한다.
- 동일하게 33.3%로 표시되는 1/3과 3333/10000은 원 수치로 구분한다.
- 현재 2페이지에 있는 기관이 비율 1위면 정렬 변경 후 1페이지 맨 위로 올라와야 한다.

## U04. 세 가지 메인 레이아웃 버튼과 기능 제거

`지도+통계 / 지도 크게 / 통계 크게`를 제거한다. 버튼을 CSS로만 감추지 않는다.

점검 경로: `CommandBar`, `FilterDrawer`에 연결된 props, `Dashboard`, `state/view.ts`의 `ViewMode`/`VIEW_LABEL`/`viewFromSearch`, URL 생성·복원, `body.dataset.view`/`main data-view`, 관련 CSS grid 분기와 테스트.

- 화면은 하나의 반응형 레이아웃을 사용한다. 같은 날짜/선택/필터가 ‘stats 크게’ 옛 모드 때문에 지도를 숨기거나 변경하지 않는다.
- 구 URL의 메인 `view=map|stats|both`는 안전하게 무시/제거해 정상 새 레이아웃으로 연다. 다른 쿼리·OAuth·공유 구성을 잃지 않게 한다.
- `state/view.ts` 전체 파일을 통째로 삭제하지 않는다. 같은 파일에 있는 관심지역·내 비교 설정·지역 라벨·별도 화면 파싱은 보존한다.
- **`screen=statistics` 맞춤 통계 페이지는 유지한다.**
- **맞춤 통계 recipe의 `view=table|chart`, 표/그래프 전환, 월별 건수/비율 전환은 유지한다.** 이름에 view가 있다는 이유로 전역 replace로 삭제하지 않는다.
- 브리핑 모드와 내 신고 비교는 별개 기능이며 이번 삭제 대상이 아니다.
- 반응형 레이아웃·KPI 가로 스크롤·표 확장에 따른 지도 크기 변화는 SDK relayout으로 처리한다. 중심/zoom/선택을 초기화하거나 지도를 재생성하지 않는다.

## U05. 법규·기관 표를 차트보다 위에 배치

확정된 순서:

1. 상단 필터바(날짜 기준 포함).
2. 지도 위 가로 한 줄 주요 통계.
3. 지도 + 지역/주소 상세 및 그 담당자 차트.
4. **위반법규별 현황(왼쪽) / 기관·담당자 처리 결과(오른쪽).**
5. **월별 추이(왼쪽) / 답변까지 걸린 기간(오른쪽).**
6. 나머지 히트맵·차량 반복일·산점도·별점 등 차트, 지역 목록·차량 TOP5·이용 안내는 기존 상대 순서를 가능한 한 보존한다.

- 모바일 DOM 순서: 법규표 → 기관/담당자표 → 월별 추이 → 처리기간.
- 시각적 CSS order만 바꾸지 말고 실제 DOM/읽기/Tab 순서도 맞춘다.
- 테이블/차트의 내부 콘텐츠가 길면 각 영역의 가로 스크롤·더 보기로 처리한다. 행 높이가 다른 두 카드를 억지로 같은 최소 높이로 늘려 큰 공백을 만들지 않는다.
- 기존 지도 크기는 사용할 수 있는 수준으로 유지하고 표를 위로 옮긴다는 이유로 지도/상세를 제거하지 않는다.
- `#entities`, 법규/지역/월별 anchor, 사이드바/하단 메뉴의 정확한 타깃과 scrollspy 순서를 새 DOM에 맞춘다.
- 실제 sticky/fixed 가림 높이+여유 공간을 측정하는 기존 스크롤 보정과 뒤로/앞으로 복원을 유지한다. KPI는 새 sticky 높이에 포함하지 않는다(고정되지 않으므로).
- 스크롤에 따라 메뉴가 활성화되고, 맞춤 통계 화면의 hidden 대시보드가 활성 판정을 덮지 않게 한다.
- 레이아웃 변경으로 지도 인스턴스·차트 인스턴스가 불필요하게 재생성되지 않는지 확인한다.

## 6. D01~D17 감사 항목의 최종 처리표

과거 감사의 ‘답변일 고정’ 대신 이번 **선택 기준 단일 집합**을 적용한다.

| D01 이중 집합 | U01: date_basis 정본+단일 cohort selector, 모든 지표 연결 |

### 7.1 엑셀·공유와 이전 기능 회귀

- Excelize/WASM, 편집 가능한 차트, 히트맵 조건부서식, 통계표·조회조건·차트데이터 시트를 유지한다. CSV 대체 금지.
- 내보내기는 **실제 표시 snapshot**을 사용한다. draft/요청중 조건을 새 제목으로 붙여 옛 수치를 저장하지 않는다.
- 조회조건에 date_basis와 기간, focus의 주소/지역/적용bbox, 실제 집계 범위, 데이터/정책 버전, 부분기간 설명을 넣는다.
- 월별 차트의 범주·셀·분자/분모·null·정렬은 화면과 동일 모델로 생성한다. exporter에서 다른 날짜로 재선택하지 않는다.
- 로컬 표/그래프 전환·범례 토글·월별 지표 체크 때문에 DB 요청을 만들지 않는다. 범례 숨김은 표·합계·분모를 바꾸지 않는다.
- 공유 링크는 선택 기준을 보존하고 수신자 권한으로 재조회한다. 개인 원자료·토큰·계정ID를 URL에 넣지 않는다. 주소/세밀한 bbox 공유 제외에 대한 기존 동의 확인 동작을 유지한다.
- WASM을 메인 초기 bundle/Edge 공용 import에 섞지 않는다. COOP/COEP·격리 service worker·SharedArrayBuffer를 새로 도입하지 않는 기존 조건을 유지한다.

### 7.2 실제 실행 순서

1. 최신 HEAD·미커밋·배포/미병합 상태를 확인하고 기존 지시와 충돌 표를 작성한다.
2. 이 문서의 독립 fixture와 같은 경계 사례로 현행 이중집합/경합/대표선정 재현 테스트를 만든다.
3. 공통 계약·canonical/date selector·활성 RPC를 수정한다. 공개/개인/포커스/월별/맞춤을 연결한다.
4. 두 날짜 UI·초안/적용/복원·캐시 키·정밀조회와 로딩 경합을 수정한다.
5. 포커스 주요 통계·복합정렬·단일 레이아웃·표 순서와 스크롤을 구현한다.
6. 공유·기존 설정 이관·표/차트·Excelize·안내를 새 정의로 맞춘다.
7. 자동검사, 실제 런타임 통합, 브라우저 검사, 파일 검증을 실행한다. 운영 적용은 별도 승인 후다.

원래 기대값을 현재 구현 출력에 맞춰 바꾸지 않는다. 정의 변경은 사용자 확정 표·fixture에 근거해 기존 테스트를 이관하고, 삭제/수정한 테스트의 이유를 남긴다.

## 8. 인수·성능·보고

동봉 `ACCEPTANCE_TESTS.md`와 `fixtures/cohort-oracle.json`을 읽고 실제 코드에 맞는 테스트를 추가한다. fixture는 합성 계약 예시이므로 저장소 helper로 변환할 수 있지만 날짜·identity·처분·기대 분자/분모를 바꾸지 않는다. fixture의 독립 기대값 점검은 앱/SQL/브라우저 인수 통과가 아니다.

필수 검증 환경:

- 단위/계약: 두 기준의 같은기간·다른결과, 한 날짜 결측, 역전, KST 경계, 전체/내, 분모0, 원비율 정렬, 각 시리즈 날짜축.
- 실제 로컬 PostgreSQL: 최신 대표 선정 전후 순서, 현재/직전기간 분리, 두 날짜 기준 SQL, 권한/함수 시그니처, 행 한도와 필터.
- 실제 Edge Runtime: 두 함수 import/번들/기동·RPC/응답 계약. Vite build를 Edge 기동 성공으로 대신하지 않는다.
- browser-mock: 응답 지연·반전·취소·동일날짜 basis전환·pin P1/P2·정렬 페이지·스토리지/URL 복원·map instance.
- real-sdk: 주소 선택·해제·클러스터 확대·Polygon·줌·드래그·중심보존. MOCK 직접 __click을 실제 SDK 검수로 적지 않는다.
- 반응형: 1920/1440/1280/768/390 × 다크/라이트, 실제 브라우저 확대율125/150/200%와 키보드 입력. viewport/DSF 에뮬레이션은 별도 판정이다.
- XLSX: 실제 브라우저에서 생성한 파일의 숫자·분자/분모·범주·순서·조회조건·차트 참조·개인정보·복구 경고를 검사한다. Excel 실기능 검사 불가 시 명시한다.

현재 프로젝트에 존재하는 test/build/scan 및 브라우저 스크립트를 확인해 실행한다. 임의로 예전 성공 숫자를 최종 결과처럼 복사하지 않는다. 테스트 스크립트는 기능 assertion 실패 시 non-zero, 미실행/환경차단은 PASS와 구분한다. 콘솔 오류 없음만으로 기능을 PASS로 하지 않는다.

운영 DB·로그·실제 신고 자료를 이번 prompt만으로 반복 검색하거나 수정하지 않는다. 권한/환경이 없으면 정확한 필요조건을 한 번에 적고 BLOCKED로 남긴다. 로컬 가능한 구현은 마무리한다.

### 배포 호환성

이 변경은 단순 추가 필드가 아니라 기존 `report_count`·집계 basis 의미 변경을 포함한다. 구 서버 응답을 새 클라이언트가 새 의미로 조용히 읽게 하면 안 된다. 새 정책/응답 버전 검사와 기존 클라이언트 전환 계획을 작성한다.

권장 순서: 필요한 증분 DB/RPC 확인·승인 → Edge 실제 검증/배포 → 새 계약 확인 → Pages → 실제 SDK/두 테스트 계정 smoke. main 병합이 Pages 배포를 촉발하면 승인/순서를 먼저 맞춘다.

### 완료 보고 형식

- U01~U05: 변경 파일, 서버·클라이언트 연결, 사용자 동작, 테스트 ID/결과, 브라우저 증거.
- D01~D17: 수정/재현되지 않음/미구현/환경차단 등 근거 있는 판정. 과거 답변일 고정 처방을 적용했다고 보고하지 않는다.
- 응답계약/정책/URL/저장구성/공유 이관, 정렬 키, 포커스요약 필드와 분모 사전.
- 최종 코드 SHA, 그 SHA를 검사한 증거 SHA, dirty 여부, SDK·자료·서버·브라우저 환경.
- PASS / FAIL / PARTIAL / NOT_RUN / NOT_IMPLEMENTED / BLOCKED / N/A를 구분한다.
- 운영 적용 여부·남은 migration/Edge/Pages 작업·승인 필요사항을 구분한다.

**마감의 핵심:** 기준 선택기를 붙이는 것만으로 끝내지 말고, 선택 날짜로 고른 같은 신고 집합을 모든 값과 표시 상태가 설명하도록 만들어라. 반대쪽 날짜가 기간 밖인 정상 신고는 숨기지 말고, 다른 조건/계정의 늦은 응답은 섞지 말라.
