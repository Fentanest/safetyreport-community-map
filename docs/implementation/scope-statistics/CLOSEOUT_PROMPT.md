## C01. 닉네임 기반 계정 구분 키 제거 — 우선 수정

### 확인된 구조
- src/pages/Dashboard.tsx의 sessionKey는 auth.status, auth.displayName, fixture를 연결한 값이다.
- 해당 값이 useDashboardData에 전달되고, StatisticsPage의 viewer로도 전달된다.
- src/auth/mapAuth.ts의 AuthSnapshot은 닉네임은 갖지만 계정 구분용 안정 식별자는 제공하지 않는다.
- src/state/statistics.ts의 readSession(viewer)는 저장된 viewer 문자열과의 일치로 설정 복원 여부를 결정한다.

서로 다른 계정에 같은 닉네임이 있으면 같은 키가 된다. 서버의 JWT 검증과는 별도로, 프론트 캐시·복원·늦은 응답을 계정별로 구분하는 경계가 부정확하다. 실제 타 계정 정보가 노출됐다고 단정하지 말고 해당 경로를 재현·수정하라.

### 요구
1. 인증 클라이언트가 제공하는 실제 사용자 ID를 내부 viewer identity로 사용한다. 필요하면 로그인 세션의 세대(epoch)를 별도로 둔다. 서버의 권한 판단은 계속 검증된 JWT의 사용자 기준이다.
2. 닉네임·이메일을 계정 식별자로 사용하지 않는다. JWT 문자열 자체를 캐시 키로 저장하거나 URL·로그로 노출하지 않는다.
3. 로그인 종료·계정 변경·권한 상실 시 이전 dashboard/personal/statistics 결과, 주소 상세, 대상 선택 후보, 선택 초안, handoff, 실행 중 요청, 활동 표시를 일관되게 정리한다.
4. 계정 A의 늦은 응답이 B의 화면·저장 상태·로딩 상태를 변경하지 못하게 viewer identity와 request generation을 함께 검증한다.
5. StatisticsPage에서 viewer 변경 effect와 저장 effect가 같은 렌더에서 실행되며 이전 draft를 새 viewer 소유로 저장하는 경로가 없는지 확인한다. restored/lastHandoff/runRef/catalog 등 ref와 state도 경계에 맞게 갱신한다.
6. 기존 닉네임 기반 sessionStorage 데이터는 새 계정으로 추정 이관하지 말고 안전하게 무효화한다. 저장한 recipe의 주소 필터·라벨·개인 문맥도 함께 감사한다.
7. 동일 사용자 닉네임 변경이나 정상 토큰 갱신 때문에 불필요한 전체 재조회·로그아웃 루프가 생기지 않게 한다.

### 인수
- UID가 다르고 닉네임이 같은 A/B 계정으로 전환한다.
- A 요청을 지연시킨 상태에서 B로 전환하고 A 응답을 뒤늦게 도착시킨다.
- A/B의 내 신고·선택 주소·설정·캐시·로딩이 섞이지 않는다.
- 같은 UID의 닉네임 변경은 계정 변경으로 오인하지 않는다.
- 로그아웃 후 새로고침, 다른 탭 인증 상태 변화, 동의 철회도 검증한다.
- 코드 테스트와 실제 브라우저 테스트 결과를 구분해 기록한다.

## C02. 비교 모드 히트맵에서 내 신고 누락 수정

### 확인된 구조
src/components/stats/PivotChart.tsx에서 compare일 때 sides=['all','mine']를 만들지만, heatmap 분기는 cell(sides[0], ...)와 heatmap:${metric}:${sides[0]}만 사용한다. 같은 결과 객체를 받는 것만으로 표/차트 비교 동등성이 충족되지는 않는다.

### 요구
1. 기관×법규 등 히트맵 조합에서도 전체와 내 신고를 모두 표현한다.
2. 기본은 동일 행·열 순서의 전체/내 신고 두 히트맵이다. 넓은 화면에서는 병렬, 좁은 화면에서는 세로 배치한다. 다른 방식이 필요하면 명시적 집단 선택을 제공하고 지금 어떤 집단을 표시하는지 분명히 알린다. compare 설정을 유지하면서 전체만 조용히 그리면 안 된다.
3. 두 히트맵은 같은 member key, 정렬, 기간, 필터, dataset version, 주 지표를 사용한다. 비율은 양쪽 모두 0~100% 고정 스케일을 사용한다. 건수·금액은 비교 가능한 공통 스케일을 사용하거나 차이를 명시한다.
4. 표의 같은 cell에 대응하는 value/numerator/denominator를 툴팁에 표시한다. 내 데이터 부재를 전체 값으로 대체하지 않는다.
5. 완전한 결과에 두 집단이 이미 있으면 표시 전환만으로 서버에 다시 조회하지 않는다.
6. 선택한 멤버, 전체/내 신고, 현재 차원, 주 지표가 다른 차트 분기에서도 몰래 누락되는지 함께 점검한다. 지원할 수 없는 조합은 이유를 표시한다.

### 인수
- 전체 수용률 50%, 내 수용률 100%처럼 차이가 나는 동일 cell을 준비한다.
- 표→히트맵→표에서 양쪽 수치와 분모가 유지된다.
- 내 신고 0건, 유효 분모 없음, 전체와 내가 같은 값인 경우도 검사한다.
- 비교 OFF, mine 단독, compare 세 가지 모집단을 각각 검사한다.

## C03. 브라우저 관찰 스크립트를 자동 합격/실패 검사로 보강

### 확인된 구조
scripts/browser/verify_scope_statistics.mjs는 많은 관찰값을 JSON에 기록한다. step()은 예외를 결과의 error로 기록한 뒤 삼키며, 마지막에 JSON을 저장하고 종료한다. 핵심 경로에도 catch(()=>undefined)가 있다. 기존 JSON을 읽어 일부 결과를 덮어쓰는 구조도 있다.

스크린샷·관찰 JSON은 증거로 유용하지만, 예외 없이 실행되었다는 사실과 기대 동작을 자동 검증했다는 사실은 다르다.

### 요구
1. Playwright expect 또는 동등한 assertion으로 요구별 기대값을 판정한다.
2. 하나라도 필수 검사가 실패하면 스크립트·CI가 non-zero로 종료한다. 실패 후 다른 검사를 계속 수행할 수는 있으나 최종 실패 상태는 유지한다.
3. 클릭·입력·차트 전환 등 핵심 동작의 오류를 무시하지 않는다. 계속 진행을 위한 catch라면 해당 ID를 FAIL로 기록한다.
4. 각 실행에 run_id, commit, 시간, 브라우저, viewport, zoom, 테마, SDK 종류, 데이터 종류를 기록한다. 새 실행 결과는 별도 파일 또는 초기화된 결과로 작성한다.
5. ONLY 부분 실행 시 미실행 항목은 NOT_RUN이다. 이전 실행의 PASS가 이번 전체 검사 결과처럼 남지 않게 한다.
6. 고정 sleep 중심 확인을 DOM·응답·상태 기반의 제한 시간 polling/assertion으로 보강한다. 고정 sleep을 썼다는 이유만으로 모두 지울 필요는 없으나 기대값 검사가 빠지면 안 된다.
7. 429를 의도적으로 주입한 테스트의 예상 네트워크 오류와 의도하지 않은 console/pageerror를 구분한다. 전체 오류 로그를 광범위하게 무시하지 않는다.
8. JSON의 true/false를 사람이 나중에 읽는 것에만 의존하지 않는다. 예: series 수, requests=0, sameInstance, selected 개수, overflow=false, 스티키 offset 허용오차를 실제 assert한다.
9. 의도적으로 기대값 하나를 틀렸을 때 실제 종료 코드가 실패가 되는지 테스트 자체를 검증한다. fixture의 정답을 구현 결과로 바꾸지 않는다.

중요 assertion 예:
- 월별 체크 1~4개 → 해당 전체 series 수, 비교 ON → 최대 8개와 정확한 series ID.
- 체크 20회/표↔그래프 → 재조회 0 및 동일 chart instance.
- 동일 핀 재클릭 → selected 0, 기본 범위 패널 복귀.
- 비율 지도 → 원형 핀 및 선택 overlay 0.
- A→B 지연 응답 → B의 제목·숫자·로딩 유지.
- 모든 시험 폭/테마 → 페이지 가로 넘침 없음, 예상하지 않은 콘솔 오류 없음.
- 스티키 이동 → 헤더 아래 12px의 허용오차 내 위치.

## C04. 실제 카카오 SDK와 실제 인증·데이터 연결의 검증 분리

REPORT.md는 합성 데이터 + MOCK 카카오 SDK로 검수했음을 명시한다. 이를 실제 SDK 검수로 바꾸어 보고하지 않는다.

1. 합성 데이터는 유지해도 되지만 실제 Kakao Maps SDK를 사용하는 별도 브라우저 검증 경로를 만든다.
2. 실제 마우스/터치/키보드로 선택, 재클릭, 빈 지도 클릭, drag, wheel, 지도 조작 버튼, 클러스터 확대, 행정구역 전환을 검사한다. __click(), __blankClick()만 호출한 결과로 대체하지 않는다.
3. 400/300ms 무시 창이 빠른 정상 재클릭을 막거나 실제 이벤트 전파를 우연히 가리는지 확인한다. SDK의 실제 이벤트 동작에 맞춰 보정한다.
4. 두 테스트 계정의 인증 변경·동의/열람 자격 변경을 UI와 API 양쪽에서 검사한다. 운영 이용자의 동의를 임의 변경하지 말고 승인된 테스트 환경/계정을 사용한다.
5. Docker 전용으로 건너뛴 41건을 모두 새 결함으로 간주하지는 않는다. 다만 이번 변경과 관련된 RPC·권한·snapshot 테스트가 무엇인지 분류하고 가능한 로컬 Supabase/Docker 또는 승인된 테스트 DB에서 실행한다.
6. 키·도메인 등록·테스트 계정 때문에 실제 검증이 불가능하면 정확한 차단 요건과 재현 절차를 남기고 BLOCKED로 기록한다. 이를 이유로 C01~C03 등의 가능한 코드 수정까지 멈추지 않는다.

## C05. 비교 대상의 0건과 이용 불가/확인 불가 구분

기존 MS-10을 마무리한다.

- 현재 권한에서 존재와 이용 가능성이 확인되었지만 현재 날짜·필터에만 결과가 없는 대상: 현재 조건 0건.
- 권한·공개 정책 등으로 더 이상 확인/사용할 수 없는 대상: 이용 불가 또는 확인할 수 없음.
- 후보 검색 실패·응답 미수신: 조회 실패/확인 중. 0건으로 치환하지 않는다.

서버가 허용된 범위에서 선택 key의 상태를 검증한다. 확인할 수 없는 대상에 대해 실제 존재 여부·소유자·철회 이유를 과다 노출하지 않는다. 권한 밖 대상을 모두 조회해서 차이를 만드는 방식은 금지한다. 과거 사용자가 저장한 로컬 라벨과 새 서버의 공개 가능 정보도 구분한다.

미확인 key를 삭제하고 전체로 몰래 변경하지 않는다. 실행을 막거나 현재 제외 상태를 명시하고 사용자가 대상을 정리하도록 한다. 임의 key 입력·다른 계정 저장 key·삭제/정책 변경·단순 필터 0건을 각각 검사한다.

## C06. 스크롤 메뉴 활성화·확대율·뒤로가기 복원 마감

1. scrollspy를 구현하여 스크롤로 지역·기관·추이 섹션에 도착해도 현재 메뉴가 바뀌게 한다. 기존 sticky inset을 재사용한다.
2. 프로그래밍 이동 중 일시적인 섹션 통과와 사용자 수동 스크롤을 구분한다. 통계 화면에서는 숨겨진 Dashboard의 섹션이 현재 메뉴를 가로채지 않는다.
3. 125/150/200% 브라우저 확대율을 검사한다. viewport 폭만 바꾸거나 deviceScaleFactor만 바꾼 것을 동일 검사로 기록하지 않는다.
4. 지도→통계→뒤로/앞으로 이동 시 화면뿐 아니라 이전 스크롤 위치·지도 중심/줌·작성 중 구성·현재 필터가 복원되는지 확인한다.
5. 비동기 데이터와 폰트 로딩 이후 제목이 sticky bar 뒤로 숨지 않는지 확인한다.
6. 주소 패널의 breadcrumb도 실제 클릭하여 상위 지역과 필터가 일치하는지 검수한다.

## C07. 요구사항 판정과 선택 기능 분리

- 430개 테스트 통과와 신규 46개라는 수치를 인수 항목 전체의 통과로 대체하지 않는다.
- 기존 REPORT.md의 PARTIAL에는 미구현과 미실행이 섞여 있다. NOT_IMPLEMENTED, NOT_RUN, PARTIAL, PASS, FAIL, BLOCKED로 구분한다. PASS에는 방식과 증거를 붙인다.
- 현재 범례가 읽기 전용이면 ‘범례를 눌러 숨기는 동작’의 테스트를 PASS로 기록하지 않는다. 원래 정한 범례 토글을 구현하여 표현만 바꾸고 분석 대상·분모는 유지하거나, 미구현으로 명시한다.
- 결과가 항상 complete이기 때문에 실제로 적용되지 않는 페이지 결과 경로는 설계상 N/A로 근거를 적는다. 그 대신 결과 한도 초과 거부·선택 대상 전체 반영을 실행해 검증한다.
- CSV는 원지시서에서 선택 기능이므로 이번 마감의 우선순위에서 제외해도 된다.
- 공유 링크는 원지시서의 저장/공유 요구와 비교하여 현재 미구현 범위를 분명히 적는다. 임의로 완료나 사용자 승인 보류로 바꾸지 않는다. 핵심 결함 수정과 분리해 구현/보류 판단을 요청한다.
- Opus 단독 구현·검수를 실제 외부 모델 독립 검수처럼 표현하지 않는다. 외부 모델 호출 자체를 마감의 전제조건으로 만들 필요는 없다.

## C08. 통합·배포·최종 보고

현재 main과 작업 브랜치가 다르므로, 검증한 정확한 커밋과 merge/build/deploy 여부를 각각 구분한다. 이 지시서만으로 운영 배포나 다른 계정 변경을 승인받았다고 해석하지 않는다.

- 코드 수정 후 해당 테스트 및 기존 회귀 검사, build, scan을 실행한다.
- DB 변경이 정말 없는지 확인하고, 필요하면 새 증분 migration을 작성한다.
- 승인 후 서버 계약 배포와 Pages 프론트 적용 순서를 검토한다. 이 작업의 public-analytics와 my-analytics 변경을 프론트 배포만으로 대체하지 않는다.
- 실제 배포 후 별도 smoke에서 catalog/candidates/query, 전체/내 신고, 지역 상세, 월별 복수 지표, 실제 지도 조작을 확인한다.
- 검수 증거에는 합성/mock, 실제 SDK+합성 자료, 실제 Supabase 테스트 환경, 운영 환경을 구분한다.

최종 보고 표:
C01~C08 | 수정 파일 | 재현 전 결과 | 수정 후 assertion | 브라우저/SDK/데이터 환경 | 증거 | 운영 적용 여부 | 남은 항목

보고서에 미구현을 숨기거나 mock 통과를 운영 통과라고 쓰지 말라. 이번 라운드는 전면 재설계가 아니라 기존 구현의 정확성·계정 구분·검수 신뢰성·미완료 요구를 마무리하는 작업이다.
