# 개인정보·보안·남용 방지

이 문서는 제품 설계 기준이며 법률 자문을 대신하지 않는다. 운영 전 실제 개인정보 처리방침, SMS 사업자와 Supabase의 처리·국외 이전 조건을 별도로 검토한다.

## 1. 개인정보 범위

### 신고자

- 휴대폰번호는 개인정보다.
- Supabase 사용자 UUID는 단독으로 공개하지 않더라도 내부에서 전화번호와 연결되는 가명 식별자다.
- 사용자가 신고한 위치들의 집합은 활동 패턴이 될 수 있다.

### 피신고자와 제3자

- 차량번호, 신고내용, 첨부자료, 정확한 발생시각을 받지 않는다.
- 주소·좌표는 도로의 위반 발생 위치로만 처리한다.
- 주택 상세주소나 다른 정보와 결합해 개인을 식별할 가능성이 있으면 정규화 또는 공개 제한한다.

### 담당자

담당자 이름은 공식 답변에 직무상 성명으로 표시되는 정보이며, 비공개 원본 영역의 `manager_counts`로 수집·저장한다. 공개 지도와 공개 API에는 포함하지 않는다. 두 레포의 현재 지도 집계 경로에는 담당자가 없으므로 업로드 DTO 생성 시 담당자 집계를 별도로 추가한다. 공개 전환은 목적·필요성·오인 또는 부당한 압력 위험을 별도로 검토한 뒤 결정한다(ADR-004).

## 2. 동의 원칙

기존 안전신문고 만족도 기능을 위해 입력한 번호를 공동 지도 용도로 자동 전송하지 않는다. 공동 지도 참여는 기본값을 꺼두고 별도 동의를 받는다.

동의 문구 초안:

> 공동 신고 지도 기여자 중복 식별과 데이터 신뢰성 확보를 위해 휴대폰번호를 수집·이용합니다. 휴대폰번호는 SMS 본인확인과 중복 방지에 사용되며 공개 지도와 통계에는 표시되지 않습니다. 동의를 거부해도 기존 앱 기능을 사용할 수 있으나 공동 지도 데이터 제공에는 참여할 수 없습니다.

동의 화면에 최소한 다음을 표시한다.

- 수집 항목
- 수집·이용 목적
- 보유·이용 기간
- 동의 거부 권리
- 거부 시 제한되는 기능
- Supabase와 SMS 사업자의 역할
- 철회·삭제 방법
- 개인정보 문의 채널

## 3. 전화번호 처리

- OTP 확인 전 번호를 고유 사용자로 인정하지 않는다.
- 번호는 E.164로 정규화한다.
- 전화번호를 기여 테이블, 분석 이벤트 또는 앱 로그에 복제하지 않는다.
- 기여 테이블은 `auth.users.id`만 참조한다.
- 관리자 화면에서 전화번호를 조회할 수 있는 인원을 최소화한다.
- 계정 삭제와 번호 변경 절차를 제공한다.

집계 기준은 `한 사람`이 아니라 `인증된 휴대폰번호`다. 한 사람이 여러 번호를 보유하거나 번호가 재할당될 수 있다는 한계를 문서와 운영 규칙에 반영한다.

## 4. 위협 모델

| 위협 | 대응 |
|---|---|
| 임의 번호로 다중 계정 생성 | SMS OTP 필수 |
| 한 사람이 여러 번호 사용 | 기여자 수만 신뢰하지 않고 이상치·교차 출처 검사 |
| 앱 변조 후 허위 건수 전송 | Edge Function 스키마·범위·증가율 검증, 격리 |
| 같은 데이터 반복 전송 | payload hash 멱등 처리, 사용자당 활성 스냅샷 하나 |
| 모바일·서버 이중 집계 | 동일 Phone Auth UUID로 스냅샷 교체 |
| JWT 탈취 | TLS, 짧은 access token, refresh token 안전 저장·회전 |
| DB 직접 쓰기 | RLS 기본 거부, Edge Function만 서비스 역할 사용 |
| 공개 API로 사용자 추적 | UUID·snapshot ID 제거, 위치별 합계만 반환 |
| 전화번호 유출 | Auth 스키마 격리, 최소 관리자, 로그 마스킹 |
| SMS 비용 공격 | 전화번호·IP 제한, CAPTCHA/Turnstile 검토, 일일 예산 경보 |
| 낮은 표본의 오해 | contributor count와 confidence 표시, 임계값 설정 |

## 5. 서버 검증 우선

Flutter와 Python 클라이언트의 검증은 사용자 경험을 위한 것이며 보안 경계가 아니다. 공격자는 클라이언트를 수정해 직접 HTTP 요청을 보낼 수 있다.

따라서 다음 검증은 Edge Function에서 다시 수행한다.

- JWT 서명·만료·issuer·audience
- 전화번호 확인 여부
- 참여 동의 상태
- 허용된 JSON 필드만 존재하는지
- 좌표와 문자열 범위
- 건수 간 논리 관계
- payload와 청크 해시
- 사용자·IP별 빈도
- 이전 스냅샷 대비 비정상 증가

## 6. 공개 기준

- 정확한 좌표와 주소는 지도 목적에 필요하므로 공개 가능 필드로 둔다.
- 개별 기여자가 어느 지점들을 제공했는지 연결할 수 있는 키는 공개하지 않는다.
- `contributor_count`는 합계 숫자만 제공한다.
- 단일 기여자 지점은 `low` 신뢰도로 표시하거나 운영 정책에 따라 숨긴다.
- 공개 응답에는 담당자 이름을 기본적으로 넣지 않는다.
- 공개 지점에서 개인 주거지를 추정할 수 있는 사례는 신고·삭제할 수 있게 한다.

## 7. 비밀 관리

Edge Function secret:

- Supabase service role 또는 secret key
- SMS provider secret
- webhook 검증 secret
- 선택적인 HMAC pepper

비밀은 저장소, Pages, APK 또는 Docker 이미지에 넣지 않는다. 키 유출 시 교체 절차와 담당자를 운영 문서에 기록한다.

## 8. 로그

허용:

- 무작위 request ID
- 성공·실패 코드
- 처리 지점 수와 응답시간
- 익명화 또는 짧게 보존하는 남용 탐지 정보

금지:

- 휴대폰번호와 OTP
- Authorization 헤더와 JWT
- 주소가 포함된 전체 요청 본문
- 담당자 이름이 포함된 payload
- Supabase·SMS 비밀키

## 9. 철회와 삭제

사용자가 참여를 철회하면:

1. 새 업로드를 차단한다.
2. staged·active·superseded 스냅샷을 삭제한다.
3. 해당 사용자를 제외해 공개 집계를 재생성한다.
4. API·CDN 캐시를 무효화한다.
5. 계정 삭제를 선택하면 Supabase Auth 사용자도 삭제한다.
6. 완료 시각만 개인정보 없이 감사 기록으로 남긴다.
